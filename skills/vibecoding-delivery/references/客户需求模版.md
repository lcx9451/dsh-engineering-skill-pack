# 第二部分：开发中要确认的技术事项

## A. 数据与精度

| 事项            | 默认方案                                                | 你改的话会怎样                                | 确认 |
| --------------- | ------------------------------------------------------- | --------------------------------------------- | ---- |
| 金额精度与币种  | 整数分存储，单一币种                                    | 多币种要另定汇率与精度规则，报表全部要改      | 同意 |
| 时间与时区      | 一律 UTC 存储，展示按本地时区                           | 混用本地时间会在跨时区/跨夏令时出错，排查极难 | 同意 |
| 敏感信息（PII） | 按"有 PII"从严：加密存储 + 日志脱敏 + 保留期 + 删除能力 | 后期才加要全量迁移并改所有读写路径            | 同意 |
| 数据保留期      | 敏感数据 90 天，业务数据 3 年（要改告诉我）             | 保留太久有合规风险，太短会丢历史              | 同意 |

## B. 并发与幂等

| 事项                   | 默认方案                                       | 你改的话会怎样                           | 确认 |
| ---------------------- | ---------------------------------------------- | ---------------------------------------- | ---- |
| 两个人同时改同一条记录 | 关键数据拒绝并提示冲突；非关键允许覆盖但留记录 | 决定锁策略，改动波及并发测试全集         | 同意 |
| 重复提交（手抖点两次） | 提交幂等，第二次返回同一结果，不重复扣费/入库  | 不幂等会造成重复数据，事后清理很麻烦     | 同意 |
| 幂等有效窗口           | 24 小时内同一请求返回首次结果，之后算新请求    | 窗口太长会挡住正常的重做，太短会重复执行 | 同意 |

## C. 失败与重试

| 事项                                  | 默认方案                                                             | 你改的话会怎样                           | 确认 |
| ------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------- | ---- |
| 处理超时/第三方没响应时，用户看到什么 | 显示"处理中"并可查询，不显示技术错误                                 | 显示原始错误会泄露内部信息且用户看不懂   | 同意 |
| 哪些错误自动重试                      | 网络超时、对方 5xx 自动重试 3 次（指数退避）；参数错、没权限立刻失败 | 乱重试会放大故障，该重试的不重试会丢任务 | 同意 |
| 批量任务部分失败                      | 成功的入库，失败的可导出并重跑                                       | 全批回滚会让用户白干，全批通过会带脏数据 | 同意 |

## D. 容量与性能

| 事项              | 默认方案                                          | 你改的话会怎样                         | 确认 |
| ----------------- | ------------------------------------------------- | -------------------------------------- | ---- |

| 页面/接口响应目标 | 1 秒内必须有反馈；接口 P95 ≤ 500ms                | 目标越高成本越高，需要提前说           | 同意 |
| 单个批量任务上限  | 1000 条 / 10 分钟内完成，超出转异步               | 上限决定内存与超时设置，改起来要动架构 | 同意 |
| 可用性与恢复目标  | 每月 99.9%；坏了 1 小时内恢复；最多丢 15 分钟数据 | 这是成本大头，要求越高越贵             | 同意 |

## E. 权限与安全

| 事项                 | 默认方案                                         | 你改的话会怎样                         | 确认 |
