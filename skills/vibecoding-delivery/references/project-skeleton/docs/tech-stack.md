> 本文件是**版本唯一源**。选型理由与备选方案写在 ADR 里，这里只写"定了什么、锁在哪个版本、为什么它可验证"。

## 一、选型原则（按重要性排序）

1. **越可验证越好**：有成熟测试框架与 CI 生态，能机械判定对错
2. **生态越成熟越好**：文档齐全、社区活跃、有长期维护承诺（含 LTS 与安全公告渠道）
3. **团队越熟悉越好**：降低学习与维护风险
4. **退出成本可接受**：不被单一供应商锁死，数据可导出、协议可迁移
5. **运维成本可承担**：优先托管方案；自建组件必须有人能值班
6. **合规可用**：满足 `PRD.md` 第 8 节要求（数据落地区域、资质、DPA）

## 三、版本锁定策略

- [ ] lockfile（`pnpm-lock.yaml`）入库，CI 用 **frozen install**（`pnpm install --frozen-lockfile`）
- [ ] 运行时与包管理器版本写进 `package.json`（`engines` / `packageManager`）与 `.nvmrc`
- [ ] 依赖升级走独立 PR，禁止与功能改动混提
- [ ] 依赖分三类策略：**运行时依赖**（锁死小版本）/ **开发依赖**（允许 minor）/ **工具链**（跟随 LTS）
- [ ] 每月一次依赖巡检：安全公告 + 升级窗口，结论记入本文件末尾
- [ ] 禁止使用 `latest` / 范围过宽的 `^` 于运行时核心依赖

## 四、被明确否决的方案

| 方案 | 否决理由 | 若未来重议的条件 |
|---|---|---|
| <微服务拆分> | <当前规模不需要，运维成本大于收益> | <单服务部署频率成为瓶颈> |
| <自建 K8s> | <团队无人可值班> | <有专职 SRE> |
