# Vibecoding 企业级项目创建完整工作流

## 0. 三条贯穿全程的铁律

1. **单一事实来源（SSOT）**：同一个信息只在一个文件里定义，其他地方只允许链接，禁止复制。
2. **每个阶段必须有 Gate**：Gate 未通过，禁止进入下一阶段。Gate 的判定标准必须是**可机械验证的事实**（命令通过、文件存在、数字达标），不是"感觉差不多了"。
3. **约束不写在 Prompt 里，写在能被执行的文件里**：`.cursorrules` 是建议，`CONSTRAINTS.md` + CI 才是约束。违反约束要红，红要拦合并。

## 1. 两个入口

| 入口              | 谁填            | 作用                                                                                           | 权威范围           |
| ----------------- | --------------- | ---------------------------------------------------------------------------------------------- | ------------------ |
| `客户需求模版.md` | **你（客户）**  | 需求（痛点、基线、场景、成功标准、数据与合规、规模）+ 需要你拍板的技术事项（每个都给了默认值） | **需求采集唯一源** |
| 其余全部文档      | 我（CodeAgent） | 见下节文档地图                                                                                 | 各自权威范围       |

**分工**：你只填需求与关键技术选择；语言、框架、数据库、部署细节、接口设计、表结构、测试、安全工具、日志监控、发布流程全部由我决定，你只看结论。

**开发中遇到模版没覆盖的问题**：我不会停下来等你把所有事想清楚——我会**给出推荐方案 + 不问的后果**再问你（写进 `客户需求模版.md` 第二部分对应位置，或在对话里直接问）。你回"同意"就行；不回答我就按默认走，并在关键节点再提醒一次。

## 3. 阶段总览与 Gate

> **阶段零（Step 0）：客户需求采集。** 它不产生代码，但决定后面所有阶段的输入质量；客户没填最少可开工集，团队不应开工。

| 阶段                    | Steps | 核心产出                                                         | Gate 通过条件                                                        |
| ----------------------- | ----- | ---------------------------------------------------------------- | -------------------------------------------------------------------- |
| 一、需求契约化          | 1–5   | PRD、NFR 配额、合规分级、风险册                                  | Gate 1：每条验收标准可测；每条 NFR 有数字+验证手段；风险有 owner     |
| 二、技术选型与架构      | 6–10  | 技术栈、架构、数据模型、接口契约、实施计划                       | Gate 2：不可逆决策均有 ADR；接口契约冻结 v0.1；计划每步含测试与回滚  |
| 三、工程约束（Harness） | 11–18 | Memory Bank、Agent 准则、CONSTRAINTS、测试策略、安全、可观测、CI | Gate 3：空仓库跑通"故意弄红 → 修复 → 变绿"，且红色确实拦住合并       |
| 四、受控实施            | 19–21 | 逐步实施循环、评审纪律、上下文维护                               | Gate 4：每个 Step 退出标准满足；CI 全绿；无未登记例外                |
| 五、验收与文档化        | 22–24 | E2E 验收、压测、部署文档、运维文档                               | Gate 5：部署文档能照着跑通一次；回滚实测过一次；运维文档覆盖常见故障 |
| 六、交付与迭代          | 25–28 | README、使用说明、缺陷闭环、门槛收紧                             | Gate 6：交付物齐备；验收标准全过；无未登记例外                       |

# 第零阶段：客户需求采集

### Step 0：客户填写《客户需求模版.md》

**动作**：把 `客户需求模版.md` 交给自己（或业务方）填写。**只需要填两件事：需求，以及需要拍板的技术选择。**

**需要填的**：痛点与量化基线、谁用怎么用、三个核心场景、成功标准与优先级、"不做"清单、数据来源与敏感信息（能否出境、能否交第三方）、合规勾选、规模与增长高峰形态、对接与登录方式、时间与成本上限，以及第二部分 A–G 的技术确认项（已给默认值，写"同意"即可）。

**不需要填的**：语言/框架/数据库、部署细节、接口设计、表结构、测试与覆盖率、安全工具、日志监控、发布流程——这些由 CodeAgent 决定，你只看结论。公司有强制要求的，写在模版 9.2 或第二部分 G。

**产出**：填好的 `客户需求模版.md`。

**最少可开工集（8 项，约 30 分钟）**：2.1+2.2 痛点与耗时基线、3 谁用怎么用、5 成功标准与优先级、4 三个核心场景、6.2+6.3 敏感数据与存放限制、8 合规勾选、11.1 期望时间与硬节点，外加第二部分 A–G 扫一眼。

**退出标准**：上述 8 项齐备；其余项允许留空，开发中再问。

**模版没覆盖的问题怎么办**：不停工干等——**带着推荐方案 + "不问会怎样"去问**；回"同意"即可，不回答就按默认走并在关键节点再提醒一次。只有真正阻塞的（例如"数据能不能出境"）才停下来等答复。

# 第一阶段：需求契约化

### Step 1：用业务语言描述痛点

像聊天一样把痛点讲清楚，不需要技术语言。例如："我每周要处理几十份简历，需要一个个打开提取信息填到 Excel，这个活儿又长又烦。"

**产出**：一段口语化痛点描述（可留在 `activeContext.md` 或对话里）。
**要点**：先记"现状怎么做的、耗时多少、错在哪"，这是后面一切收益判断的基准。

### Step 2：生成产品需求文档（PRD）

将项目创意提交给 AI，要求生成结构化的 Markdown 设计文档 `docs/PRD.md`。关键要求：

- 明确目标用户和使用场景
- 列出核心功能点和验收标准
- 明确**不做什么**（scope 边界）
- **每条验收标准必须写成 Given / When / Then**，且可被测试用例直接翻译
- 附术语表（业务词 ↔ 工程命名，见 Step 7 的 L3）
- 附非目标用户与非目标场景（防范围蔓延）

**退出标准**：随机抽 3 条验收标准，都能立刻写成一个自动化测试用例；"不做清单"至少 3 条。

### Step 3：补充非功能需求（NFR 配额表）

提示词越侧重异常处理和性能约束，生成的代码质量越接近资深工程师水平。但 NFR 必须**带数字**，否则等于没写。

在 PRD 中补充一张配额表：

| 维度           | 必须写清的数字                                               | 验证手段              |
| -------------- | ------------------------------------------------------------ | --------------------- |
| 响应时间       | P50 / P95 / P99（区分读写路径）                              | 压测脚本 / APM 分位图 |
| 吞吐与并发     | 峰值 QPS、并发用户数、批量任务上限                           | k6 / locust           |
| 可用性         | 月度可用性目标（如 99.9%）                                   | SLO 看板              |
| 恢复目标       | RTO / RPO                                                    | 备份恢复演练          |
| 容量与成本     | 单请求成本上限、月云成本上限                                 | 成本看板              |
| 数据规模       | 首年行数/存储量、增长率                                      | 容量规划              |
| 异常处理       | 哪些错误必须重试、重试次数与退避、哪些必须快速失败、幂等要求 | 故障注入测试          |
| 时区/编码/精度 | 金额用整数分还是 Decimal、时区一律 UTC 存储                  | 单元测试              |

**退出标准**：每条 NFR 都有数字、有验证命令或方法、有 owner。

### Step 4：合规、隐私与数据分级

企业级项目在写第一行代码前必须回答：

- **数据分级**：公开 / 内部 / 机密 / 个人敏感信息（PII），逐字段标注，落到 `docs/data-model.md`
- **合规范围**：个保法（PIPL）/ GDPR / 等保 / SOC2 / 行业监管，哪几条真实适用
- **合法性与留存**：收集依据、用户删除权、数据保留期与到期销毁机制
- **跨境与第三方**：数据是否出境、用了哪些第三方处理者、是否需要 DPA
- **审计要求**：哪些操作必须留不可篡改审计日志、保留多久

**退出标准**：`docs/data-model.md` 中每个含 PII 的字段都有分级标注；适用条款清单有明确"适用/不适用+理由"。

### Step 5：风险登记册与假设清单

新建 `docs/risks.md`：

| ID  | 风险/假设           | 类别     | 概率 | 影响 | 应对                    | Owner |
| --- | ------------------- | -------- | ---- | ---- | ----------------------- | ----- |
| R1  | 第三方 OCR 接口限流 | 外部依赖 | 中   | 高   | 本地降级方案 + 队列削峰 | @xx   |

**退出标准**：Top 5 风险均有应对方案与负责人；被证伪的假设有验证动作（放 Step 10 计划里）。

> **Gate 1 判定**：上述 Step 2–5 的退出标准全部满足，且 PRD 由至少一个非作者角色过一遍。

# 第二阶段：技术选型与架构设计

### Step 6：确定技术栈

让 AI 推荐**最简单且最健壮**的技术栈。技术栈选择原则：

- **越可验证越好**：有完善的测试框架和 CI 工具支持
- **生态越成熟越好**：文档齐全、社区活跃
- **团队越熟悉越好**：降低学习成本和维护风险
- **退出成本要评估**：被锁死的风险、迁移代价（企业级新增项）
- **运维成本要评估**：需要几个人值班、是否有托管方案
- **合规可用性**：该服务是否满足 Step 4 的合规要求（数据落地区域、认证资质）

保存为 `docs/tech-stack.md`，**明确版本号，锁定依赖**（lockfile 入库、CI 用 frozen install、包管理器版本写进 `packageManager` / `engines`）。

**同时产出 `docs/decisions/ADR-001-tech-stack.md`**，记录候选方案、否决理由、后果。之后每一个不可逆决策（数据库、鉴权、部署形态、消息中间件、ORM）都补一条 ADR。

**退出标准**：`tech-stack.md` 里每个依赖都有版本、有选它的理由、有替代方案；ADR-001 已接受。

### Step 7：生成架构草案与三级知识库

让 AI 输出轻量架构文档 `docs/architecture.md`。企业微信的三级金字塔知识库值得借鉴：

- **L1 总览** `architecture.md`：模块名 + 一句话职责，控制在 5KB 以内，每次定位默认加载
- **L2 模块** `docs/modules/<module>.md`：每个文件一行职责，按需加载
- **L3 语义桥**：把**业务语义与设计语义**翻译成工程 API 命名映射（业务词"对账批次" ↔ 代码 `ReconciliationBatch`；设计 Token `color-danger` ↔ `theme.danger`）。L3 解决的是"同一个概念在三处叫三个名字"的歧义，不是架构分层本身。

关键原则是**模块化**，禁止生成"单体巨文件"。每个模块职责单一，接口清晰。（参考：[企业微信三级知识库实践](https://cloud.tencent.cn/developer/article/2745153)）

**额外要求**：

- 画清分层与依赖方向，并明确**禁止的调用方向**（如 Controller 不得直连 DAO）——这条会在 Step 14 用 `dependency-cruiser` 机械检查
- 标注同步/异步边界、事务边界、幂等键
- 新增模块必须先在 `architecture.md` 注册（AI 准则里也要写死）

**退出标准**：L1 文档 ≤5KB；每个模块有 L2 文件；依赖规则能被工具表达。

### Step 8：数据模型与数据生命周期

- 实体关系图 + `docs/data-model.md`（字段类型、可空、默认值、索引、唯一约束、PII 分级）
- **迁移策略**：迁移文件必备、禁止手改生产库、必须可回滚或前向兼容（expand-contract 模式）
- **备份与恢复**：备份频率、异地副本、**每季度至少一次真实恢复演练**（对应 Step 3 的 RTO/RPO）
- **保留与销毁**：过期数据归档/删除的自动化任务
- 大表与热点：分页键、慢查询预算（如 P95 查询 <100ms）

**退出标准**：迁移与回滚脚本在本地环境各跑通一次（含一次"迁移到一半失败"的模拟）。

### Step 9：接口契约先行

- `docs/api/openapi.yaml`（或 tRPC/GraphQL schema）作为**唯一接口源**，代码从契约生成或校验
- 统一错误码字典、统一分页/排序/过滤约定、统一时间与金额格式
- 版本策略（URL 版本还是 header 版本）、废弃流程与通知期
- 鉴权与限流策略在每个端点标注清楚

**退出标准**：契约通过 lint（如 spectral）与 mock server 可用；前后端能各自对着 mock 开发。

### Step 10：制定实施计划

将设计文档和技术栈文档提供给 AI，生成详细的分步实施计划 `memory-bank/implementation-plan.md`。每一步应包含：

- **输入**：需要哪些前置文件和数据
- **动作**：具体做什么改动
- **产出**：预期的代码改动和文件
- **验证方式**：如何确认这一步做对了（具体命令）
- **退出标准**：满足什么条件才能进入下一步
- **测试**：本步新增/修改哪些测试（企业级新增项）
- **回滚**：本步出错怎么退回（企业级新增项）
- **规模**：单步改动建议 ≤ 400 行 diff，超出则再拆

计划中只应包含清晰的指令，而非代码。

**退出标准**：每个 Step 都能独立验证、独立回滚；第一个 Step 可在 1 小时内完成。

> **Gate 2 判定**：不可逆决策均有 ADR；接口契约冻结 v0.1；实施计划每步含测试与回滚；架构评审（人或另一 Agent 扮演评审）通过。

# 第三阶段：建立工程约束（Harness 层）

### Step 11：构建 Memory Bank

Memory Bank 是一组维护在项目根目录下的 Markdown 文件矩阵，核心在于"文档即代码"。完整的企业级 Memory Bank 结构（**权威范围见第 2 节文档地图，此处不重复定义**，参考：[Memory Bank 实践](https://cloud.tencent.cn/developer/article/2670237)）：

```
memory-bank/
├── projectbrief.md          # 项目宪法：硬性目标和约束
├── productContext.md        # 业务逻辑与用户故事
├── systemPatterns.md        # 架构规范与代码模板
├── implementation-plan.md   # 分步实施计划（权威源）
├── activeContext.md         # 运行内存：当前会话状态
└── progress.md              # 里程碑与进度记录

docs/                        # 其余权威文档（tech-stack / architecture / data-model / api / adr / CONSTRAINTS）
```

`tech-stack.md` / `architecture.md` / `implementation-plan.md`。这三者可保留软链接或只用一份；`implementation-plan.md` 归 memory-bank，其余归 `docs/`，任何一处不得存在两份内容不同的副本。

`activeContext.md` 是"运行内存"——每次任务开始前 AI 必须读取以恢复上下文，任务结束时必须强制更新。Memory Bank 的核心价值在于为编码 Agent 提供持久化的项目知识、显式治理和可重复的交付流程。

**`activeContext.md` 模板**：当前目标 / 正在做的 Step / 已改文件 / 未决问题 / 下一步第一步动作 / 已知坑。
**exit 标准**：任一新会话只读 `activeContext.md` + `architecture.md` 就能接着干，不需要翻聊天记录。

### Step 12：配置 AI 行为准则与 Agent 治理

在项目根目录创建 `AGENTS.md`（兼容 `.cursorrules` / `CLAUDE.md`，建议 AGENTS.md 为主、其余指向它）。Harness Engineering 的核心原则是：**不依赖 Prompt 约束，而是在 AI 每次产出代码后用编程检查**——检测产物中是否引用了指定组件库，如果没有，系统自动拦截并修正，同时调整上下文让 AI 后续不再犯同样的错。

示例配置：

```
AI行为准则

## 角色定位

你是拥有10年经验的高级架构师，遵循企业级代码规范。

## 代码规范

1. 所有函数必须标注入参/出参类型
2. 禁止使用全局变量，依赖注入优先
3. 错误处理必须具体到异常类型，禁止裸露的except:
4. 日志记录需包含调用链的funcName与traceId
5. 所有公共API必须有JSDoc/DocString文档

## 架构约束

1. 严格遵循memory-bank/systemPatterns.md中定义的架构模式
2. 新增模块必须先在architecture.md中注册
3. 禁止跨层调用（如Controller直接调用DAO）

## 安全红线

1. 禁止硬编码任何凭证、密钥、token
2. 所有用户输入必须经过校验和净化
3. SQL查询必须使用参数化查询

## Agent 治理（企业级新增）

1. 开始任务前必须读 activeContext.md、CONSTRAINTS.md、相关 ADR
2. 结束任务前必须更新 activeContext.md 与 progress.md
3. 禁止修改：lockfile、CI 配置、CONSTRAINTS.md、迁移脚本历史文件、docs/decisions/**
4. 禁止臆造 API：使用任何库/接口前必须查文档或源码，不得凭记忆编造参数
5. 禁止新增 @ts-ignore / eslint-disable / # noqa / 空 catch / throw new Error("Not implemented")
6. 禁止为了让检查变绿而删测试、跳过测试、下调阈值
7. 上下文预算：单次任务只加载 L1 + 本任务相关 L2，不整仓扫描
8. 不可逆决策（依赖、schema、鉴权）必须先提议 ADR 交人工确认
```

**退出标准**：治理规则中"禁止修改"清单与实际 CI 保护规则一致；`AGENTS.md` 显式指向 `CONSTRAINTS.md`。

### Step 13：配置 Linter / Formatter / 类型检查

光有文档不够，需要用工具强制执行。配置 ESLint + Prettier 或等效工具链（Python: Ruff + mypy；Go: gofmt + golangci-lint），并在 `package.json` 中添加强制执行脚本。ESLint 是代码检查工具，能自动发现代码中的问题和不规范的地方；Prettier 是代码格式化工具，能自动统一代码格式。

补充要求：

- **类型检查必须开启严格模式**（`strict: true`、Python `mypy --strict` 起步可局部放宽并登记例外）
- **pre-commit 钩子**只跑快速的（format + lint + 密钥扫描），保证 <5s，慢检查一律交给 CI
- 编辑器/CI 使用同一份配置，禁止"本地过、CI 挂"

### Step 14：把质量门槛写成可执行文件 `docs/CONSTRAINTS.md`

`CONSTRAINTS.md` 骨架：

```markdown
# Constraints（质量门槛）
Last reviewed: YYYY-MM-DD by @owner

## 底线（始终强制，无需额外工具）
- 禁止新增抑制注释：@ts-ignore / eslint-disable / # noqa / # type: ignore
- 禁止未实现桩：throw new Error("Not implemented")、空 catch {}
- 禁止无理由删除或 skip 测试
- 禁止源码中出现密钥
- 本文件不得为了让某个改动通过而被放宽

## 带数字的强制项
| 维度 | 规则 | 检查命令 | 运行时机 |
|---|---|---|---|
| 类型 | 0 类型错误 | tsc --noEmit | 每次编辑 |
| Lint | 0 error | eslint . / ruff check | 每次编辑 |
| 密钥 | 0 命中 | gitleaks detect --redact | 每次编辑 |
| 覆盖率 | 变更行 ≥ 80% | vitest run --coverage + git diff | 任务结束 / CI |
| 代码安全 | 无 high 及以上 | semgrep scan --config p/default | CI |
| 依赖安全 | 无 high 及以上 | osv-scanner scan source -r . | CI |
| 架构边界 | 0 违规 | depcruise --validate src | CI |
| 性能 | LCP ≤ 2500ms、CLS ≤ 0.1 | lighthouse $PREVIEW_URL | 预览部署 |
| 无障碍 | 0 critical/serious | axe $PREVIEW_URL | 预览部署 |

## 只测量不拦截（棘轮）
| 指标 | 当前值 | 方向 |
|---|---|---|
| 项目整体覆盖率 | 62.4% | 不得下降 |
| 主包体积 | 184 kB | 不得增长 |

## 例外（必须有 owner 与到期日，默认 90 天）
| ID | 规则 | 路径 | 原因 | Owner | 到期 |
```

规则（来自约束驱动开发实践）：

- **每一行都要有能产出结论的命令**；只有数字没有命令的条款叫愿望，不叫约束
- **至少一条约束来自项目之外**（axe / osv-scanner / Lighthouse）。全靠自己写的测试自证，是循环论证
- **棘轮代替空想指标**：现在 62% 就写 62% 并禁止下跌，而不是写 80% 然后永久红灯
- **分级预算**：编辑循环 <5s，任务结束 <90s，全量仅在 CI
- **门槛自身要设防**：评审时专门看五类"把红变绿"的小动作——下调阈值、测试被 skip/删除、抑制注释、未完成桩、新增无人认领的例外

**退出标准**：`npm run check:fast` / `check:task` / `check:full` 三个脚本在空仓库上可运行；`CONSTRAINTS.md` 每条数字在代码里有对应命令。

### Step 15：测试策略

明确写进 `docs/testing.md`（或 `systemPatterns.md` 的一节）：

- **测试金字塔与配额**：单元（多、快）/ 集成（关键路径）/ E2E（少而稳，覆盖核心业务流程）
- **覆盖率口径**：以"变更行覆盖率"为准，而不是拿历史整体覆盖率背锅
- **契约测试**：对着 OpenAPI 契约跑，防止前后端漂移
- **测试数据**：工厂/fixture 统一管理，禁止依赖生产数据快照，禁止在测试里 sleep 等异步
- **确定性**：时间、随机数、时区、网络必须可注入 mock；flaky 测试视为缺陷，不许重跑掩盖
- **AI 生成代码必带测试**：Step 10 里每步已声明测试项，**没有测试的 Step 视为未完成**
- 关键业务逻辑引入变异测试（mutation score 起点 60%）

**退出标准**：跑一次 `check:task` 全绿；故意改坏一处业务逻辑，必须有测试变红。

### Step 16：安全工程

| 层     | 动作                                                                     | 命令/工具             |
| ------ | ------------------------------------------------------------------------ | --------------------- |
| 密钥   | 集中管理（Vault / KMS / 云 Secret Manager），`.env` 不入库，仓库历史扫描 | gitleaks、git-secrets |
| 代码   | SAST + OWASP Top 10 规则集                                               | semgrep               |
| 依赖   | SCA + 锁文件 + 依赖白名单 + 定期升级窗口；产出 SBOM                      | osv-scanner、syft     |
| 供应链 | CI 使用最小权限 token，第三方 Action 固定 commit SHA                     | —                     |
| 输入   | 所有外部输入校验（schema 校验层），SQL 参数化，输出转义                  | 单元/集成测试         |
| 鉴权   | 认证与授权分离，服务端强制鉴权，禁止只靠前端隐藏                         | 越权测试用例          |
| 数据   | 传输 TLS、静态加密、日志脱敏（PII 不入日志）                             | 日志审计              |
| 审计   | 关键操作不可篡改审计日志                                                 | —                     |
| 演练   | 至少一次越权/注入/密钥泄露的防御验证                                     | 渗透/红队或自测       |

**退出标准**：SAST 与 SCA 无 high 及以上；越权测试用例存在且通过。

### Step 17：可观测性

- **结构化日志**（JSON）：必带 `traceId`、`userId`（脱敏）、`funcName`、`durationMs`、`errorType`；禁止 `print`/`console.log` 裸输出
- **链路追踪**：OpenTelemetry 接入，跨服务/跨异步任务透传 context
- **指标**：RED（Rate/Errors/Duration）+ USE（Utilization/Saturation/Errors），业务指标（如"成功处理简历数"）
- **SLO 与错误预算**：把 Step 3 的可用性目标落成 SLO，错误预算耗尽即冻结功能发布
- **告警**：只对**用户可感知的症状**告警，每条告警有 runbook 链接，禁止无动作的告警
- **相关 ID 贯通**：从网关到 DB 查询到异步队列全链路可追

**退出标准**：本地起服后能在一个面板里看到一次请求的完整链路；人为制造一个错误，日志能定位到具体函数与请求。

### Step 18：CI 流水线、分支策略与保护规则

- **门禁分级**（对应 Step 14）：`check:fast`（编辑）→ `check:task`（任务结束）→ `check:full`（CI）
- **流水线阶段**：安装（frozen lockfile）→ 静态检查 → 单元/集成测试 → 安全扫描 → 构建 → 预览部署 → E2E/Lighthouse/axe
- **分支策略**：主干开发 + 短命分支；PR 模板强制包含"改了什么的为什么 / 验收标准对应关系 / 测试证据 / 是否触碰 CONSTRAINTS 或 ADR"
- **保护规则**：主干禁止直推；必须 CI 全绿 + 至少 1 人评审；`CONSTRAINTS.md`、CI 配置、迁移脚本、ADR 目录设 CODEOWNERS
- **构建产物**：制品与镜像打版本标签，含 SBOM 与签名

> **Gate 3 判定**：在空仓库上故意制造一次类型错误、一次密钥、一次依赖漏洞，流水线三次都必须红，且红色确实阻止合并。**没做过这个演练的 CI 等于没有 CI。**

# 第四阶段：受控实施（AI 执行循环）

### Step 19：单步实施循环

每个 Step 都走同一个循环，禁止"一次性生成整个项目"：

1. **读**：`activeContext.md` + 本步相关的 L2 模块文档 + 相关 ADR + `CONSTRAINTS.md`
2. **定**：把本步拆成"先写测试"的最小切片（TDD：红 → 绿 → 重构）
3. **改**：只改本步范围内的文件；契约先行（先改 `openapi.yaml` 再改实现）
4. **验**：跑 `check:task`，失败必须自己修到绿，不许绕过
5. **审**：自查 diff 的五类偷工减料（见 Step 20）
6. **记**：更新 `activeContext.md`、`progress.md`，必要时补 ADR
7. **提**：小步提交（一个 Step 一个或多个原子提交），提交信息说明"为什么"

**退出标准**：本步的"验证方式"命令通过 + 测试通过 + 文档已更新。

### Step 20：提交前自查与 diff 守卫

评审不只看"能不能跑"，专门盯五类把红变绿的动作（用 `git diff` 就能看出来）：

1. **阈值被下调**：预算变小、严重级别降低、检查从快速阶段被移除
2. **测试被弱化**：新增 `.skip`、删测试文件、断言被抽走
3. **检查器被静音**：新增 `@ts-ignore` / `eslint-disable` / `nosemgrep` / `istanbul ignore` / `Stryker disable`
4. **活儿没干完**：抛异常的桩、空 catch、TODO 顶替实现
5. **凭空出现例外**：Exceptions 表多了一行而没人讨论过

原则：**收紧门槛应当无声，放宽门槛必须大声。**

另外，**不可逆改动必须先写 ADR 再动手**：鉴权、支付、schema 迁移、数据删除、对外接口破坏性变更、依赖新增。

### Step 21：进度与上下文维护

- 每个 Step 结束更新 `progress.md`（已完成 / 进行中 / 阻塞 + 日期）
- `activeContext.md` 每次会话必须刷新，**写清"下一步第一步动作"**，让下一个会话冷启动零成本
- 计划偏离（拆分、合并、顺序变化）同步回 `implementation-plan.md`，禁止"计划在文档里，实际做法在脑子里"
- 已知坑与新学到的约束沉淀进 `systemPatterns.md`

> **Gate 4 判定**：`implementation-plan.md` 中所有 Step 的退出标准满足；CI 全绿；`CONSTRAINTS.md` 例外表无未登记项；**收敛检查通过——没有"做了没人要的"，也没有"少做了说好的"**。

# 第五阶段：验收与文档化

> 这一阶段只做两件事：**证明它真的能用**，以及**把"怎么部署、怎么运维"写成文档**。
> 部署与运维本身不在这份工作流的管辖范围内——你要的是一份照着能做、出事能查的说明书，不是一个值班表。

### Step 22：端到端验收与性能验证

- **UAT**：按 PRD 的 Given/When/Then 逐条跑一遍，出结论表（通过 / 不通过 / 偏差）
- **收敛检查**：逐条对照 `docs/PRD.md` 与 `客户需求模版.md`，找出两类偏离——**做了没人要的**（自己加的功能、顺手优化的东西）和**少做了说好的**（悄悄缩水的验收标准、被"下一期再说"的功能）。每一项都要给出处置：**改代码，或者改 PRD 并写明为什么改**；不许两头都不动，也不许用"后续优化"糊过去
- **压测**：按 Step 3 的 P95 与峰值目标压测，记录拐点与瓶颈
- **故障注入**：断第三方依赖、断数据库、队列积压，验证降级与重试策略符合 Step 3 约定
- **数据校验**：迁移后行数、金额、关键字段一致性核对
- **安全复测**：越权、注入、限流、密钥泄露路径

**退出标准**：压测达到目标，或偏差有书面结论。

### Step 23：写部署文档 `docs/DEPLOYMENT.md`

目标：**拿这份文档，在一台干净的机器上能把系统跑起来；出问题能退回去。**

它是一次性投入，省掉以后每一次"当时到底怎么部署的来着"。必须写清：

- 三种方式各一节（单机 Docker Compose / 云托管 PaaS / 云服务器手动），你用哪种写哪种，其余保留骨架备用
- 环境变量清单：每个变量的用途、哪些敏感、怎么生成、放在哪
- 首次部署步骤、升级步骤、**回滚步骤**
- 数据库迁移怎么跑、迁移前怎么备份、迁移失败怎么办
- 部署后的验收项：健康检查 / 首页 / 日志 / 迁移已应用 / 核心流程走通 / 定时任务在跑 / 备份就绪
- 常见部署失败与处理：端口占用、缺环境变量、502、数据库连不上、时区差 8 小时、上传文件丢失、磁盘满

### Step 24：写运维文档 `docs/OPERATIONS.md`

目标：**三个月后的你（或接手的人）不用重新摸索，就知道怎么看、怎么修、怎么恢复。**

必须写清：

- **日常检查**：一条命令看健康；每天看什么、每周看什么、正常范围是多少
- **日志在哪**：应用日志、错误日志、反向代理日志的位置；怎么按 `traceId` 追一次完整请求
- **常见故障与处置**：服务起不来 / 大量 500 / 变慢 / 任务堆积 / 磁盘满 / 数据库连不上 / 证书过期 / 定时任务没跑 / 数据看着不对
- **备份与恢复**：备份命令、存放位置与保留期、**恢复步骤**、每季度真实演练一次并留记录
- **维护任务**：依赖升级、密钥轮换、日志脱敏抽查、过期数据清理
- **常用命令速查**：状态、日志、进库、备份、查磁盘

> **Gate 5 判定**：按部署文档在干净环境完整跑通一次；回滚步骤**实测成功一次**；运维文档覆盖常见故障；备份恢复演练过一次。

# 第六阶段：交付与迭代

### Step 25：交付物收尾

- `README.md`：项目是什么、怎么在本地跑起来、命令表、目录结构说明
- 所有文档的占位符填干净（全仓检索 `<`）

### Step 26：缺陷闭环

- 每个修掉的缺陷**补一条测试**，否则它会再回来一次

> **Gate 6 判定**：README 能照着把项目跑起来；验收标准全过（或未过项有书面记录）；遗留项全部登记；无密钥入库、无未实现桩、无静音检查器。

| 一次性脚本 / 数据清洗          | Step 0、1、2、10、19、20 | 其余全部                                |
| 内部工具（少量用户、内部数据） | 一~三阶段 + Step 19–24   | Step 8 演练、Step 16 部分、Step 22 压测 |
| 面向客户的生产系统             | 全量                     | 无（可降低部分数字门槛）                |
| 处理 PII / 受监管              | 全量 + Step 4 加严       | 无                                      |

**不可裁剪的底线**（无论项目多小）：

1. 需求有可测的验收标准
2. 有 `CONSTRAINTS.md` 且至少一条外部约束
3. 有 CI 且演练过"变红会拦住"
4. 有 `activeContext.md` 且会话间可冷启动
5. 无密钥入库、无未实现桩、无静音检查器
6. 上线有回滚方案

> **Step 0 也在此列**：任何项目都不可跳过"客户需求采集"——哪怕是自己给自己写的小工具，也要先把痛点、量化基线和成功标准写下来（一页纸即可）。**没有基线的项目无法验收，只能凭感觉争论。**

## 附录 B：关键提示词骨架

- **PRD**："基于以下痛点，输出 PRD：目标用户、使用场景、功能点、Given/When/Then 形式的验收标准、不做清单、术语表。不要写技术方案。"
- **NFR**："针对该 PRD，列出非功能需求配额表，每项必须有数字、单位、验证手段；无法量化的项请明确标注'暂不可量化'并给出替代验证方式。"
- **架构**："输出 L1（≤5KB，模块名+一句话职责）+ 每模块 L2，明确依赖方向与禁止的调用方向，并给出可机械检查的规则表达。禁止单体巨文件。"
- **实施计划**："把设计文档转成分步实施计划，每步含输入/动作/产出/验证命令/退出标准/测试项/回滚方式，单步 diff ≤400 行，只写指令不写代码。"
- **约束**："基于当前仓库现状，生成 CONSTRAINTS.md：底线清单、带数字维度（每行必须有检查命令与运行时机）、棘轮指标（记录当前值）、例外表（owner + 90 天到期）。数字以现状为起点，不要凭空拔高。"
